## GT New Horizons runs 🏭

The previous release got 293 of GTNH's 294 mods through pre-init and stopped at
two conflicts it called architectural: the 4096 block-id ceiling and Phosphor's
lighting. **Both are resolved, and the pack now boots** — all 294 mods, nothing
excluded, Phosphor left enabled, reaching `Done` in CI on every check.

### Chunk storage now has two backends

The conflict was never really about block ids. It was that this core stores a
chunk section as 12 KiB of off-heap memory, while every mod that lifts the id
ceiling (EndlessIDs, NEID) or replaces the lighting engine (Phosphor) works by
patching vanilla's heap arrays — and there were none to patch. Competing with
that machinery would have produced chunks no client, editor or other mod could
read. So the core now lets it work instead:

```
java -Dorg.ultramine.chunk.storage=vanilla -jar ultramine-server.jar
```

| mode | a section is | for |
|---|---|---|
| `offheap` *(default)* | one 12 KiB off-heap slot — no heap, no GC | anything inside vanilla's 4096 block ids |
| `vanilla` | vanilla's five heap arrays, live and patchable | packs whose coremods patch chunk storage |

Both hold the identical packing, so **a world is the same world in either
mode**. In `vanilla` mode the arrays *are* the section: a mod writing through
one is writing the world, and replacing one replaces the section on every path,
including the raw storage that chunk saving and the chunk packet read. The
server logs which mode it started in and warns when it finds mods that need the
other one — it never switches on its own, because chunk storage is decided
before a world is opened.

Everything else the core does — async chunk IO, adaptive chunk streaming, the
tick regulator, multiworld, permissions, economy, the mob-spawn engine, backups
— is independent of the backend and works in both.

### Crashes and one silent corruption, closed

- **Entity tracker.** Every loop in `EntityTracker` walked the live set while
  firing Forge's `StartTracking`/`StopTracking` events — and a mod handler that
  spawns an entity reaches straight back into `addEntityToTracker`. A
  `ConcurrentModificationException` took the world tick, or a player's login,
  with it. The loops now walk a snapshot rebuilt only when the set changes.
- **Chunk unloading.** The same shape: the unload queue was iterated with a live
  cursor while `onChunkUnload` fired `ChunkEvent.Unload`, and any handler that so
  much as asks for a chunk lands in `loadChunk`, which removes from that queue.
- **Recipe cache** (on by default) answered "no such recipe" from a key that
  could not know. A positive hit is re-checked; a negative one is returned as-is,
  and the key is item id and damage only — so two stacks differing solely in NBT
  shared it, and the first grid that matched nothing taught the cache that the
  second matches nothing either. **Tool modifiers, filled cells and programmed
  circuits silently stopped crafting.** Grids with NBT now bypass the cache.
- **Unidentified connections** could make the server hold two megabytes each by
  announcing a large frame and sending it slowly. The handshake and status phases
  are capped at 16 KiB; login and play keep the full range, because FML syncs the
  block and item registry during login and for a large pack that really is
  megabytes.

### Java 9+ coremod loading

Three defects that stood between a coremod pack and a modern JVM, all the same
mistake: from Java 9 the application class loader is not a `URLClassLoader`, and
the 1.7.10 stack assumes it is. Coremod jars now reach the application class
path through the door Java 9+ actually provides, the class path is read the way
launchwrapper reads it on Java 8, and the core's own ASM visitors read class
files as new as the ASM it ships.

This does not yet make GTNH run on Java 25 — what remains is third-party
bytecode that Java 8's verifier accepted and modern ones reject, in mods rather
than in the core (see [docs/06](../06-modernization-notes.md) for the exact
errors and how each was attributed). **Run coremod-heavy packs on Java 8.** The
bare server runs on Java 8 through 25 and both remain CI gates.

### Build and tests

- **Gradle 6.0.1 → 8.14.3** with a Java 8 toolchain. The reobfuscation tasks
  moved off `IncrementalTaskInputs`, removed in Gradle 8, keeping incremental
  behaviour rather than dropping it; every deprecation the build itself produced
  is gone.
- The test suite now runs the chunk storage contract against **both** backends,
  including the bulk paths chunk saving and the chunk packet use, and covers the
  live arrays, array replacement, storage-mode selection, the chunk key and the
  vanilla chunk-set adapter.
- The modpack boot test takes the storage backend and the pack variant as
  separate inputs, and a failed boot now prints the crash cause last, where the
  log is actually readable.
