## GT New Horizons boots, and shuts down without losing the world 🌍

The pack the [download page](https://www.gtnewhorizons.com/downloads/) actually
serves — `GT_New_Horizons_2.8.4_Server_Java_8.zip`, the whole pack — now starts
on this core and saves cleanly on the way out. That is verified by the modpack
gate rather than inferred: the run reaches vanilla's real `Done (Ns)! For help`
line, and shutdown ends `=== shutdown save clean ===` with no
`Exception stopping the server`.

Run it with `-Dorg.ultramine.chunk.storage=vanilla` on Java 8. Java 25 is a
separate question, answered at the bottom.

Everything below is why it did not work before, and every one of them is the
same defect wearing a different hat.

### The shape rule

Almost every modpack failure this core has had has been one shape:

> A vanilla **name** was kept while what sits behind it changed — a field's type,
> a method's body, a local variable table, an allocation site. A coremod's patch
> then misses, while the rest of its rewrite still lands, and the class fails to
> load.

It fails hard rather than softly. Mixin fails the *whole* mixin when a `@Shadow`
or an injection point does not resolve, and the target class then never loads.
One retyped field took down a packet class, and with it the server.

Four of these are fixed. Each keeps vanilla's shape alongside this core's, so
both a coremod's patch and the off-heap path find what they expect.

- **`DedicatedServer`** kept the vanilla `settings` field, of the vanilla type,
  next to this core's own config. A coremod that shadows `settings` had been
  finding a different type behind a familiar name. `server.properties` is now
  also pre-created with a header, so PropertyManager stops emitting a warning
  that read like a failure and was not.
- **`S21PacketChunkData`** — the chunk packet. Its copy loops branch on the
  storage mode with **vanilla first**, so `getBlockLSBArray()` is ordinal 0 and
  `getMetadataArray()` is ordinal 1 exactly as in vanilla. Coremods that
  `@Redirect` these by ordinal — several large packs do — resolve again.
- **`AnvilChunkLoader`** writes and reads `Blocks`, `Add`, `Data`, `BlockLight`
  and `SkyLight` as vanilla `setByteArray`/`getByteArray` NBT again, rather than
  through a private wrapper type. The write clones, which is what the old path
  did too, so the IO thread cannot observe a half-written section.
- **`MapGenStructureData.writeToNBT`** no longer throws. It had been throwing
  `IllegalStateException` on the assumption that only this core would ever call
  it. A coremod called it, and **every world after the first went unsaved.**
  Never leave a tripwire in a public vanilla method.

### A login race that could duplicate a player

Two connections for the same account, arriving close enough together, could both
pass the "already online" check before either had finished loading. The window
was small and entirely real: player data is loaded asynchronously, and the check
sat before the load rather than around it.

Logins now take a claim on the account for the duration, released when the player
is in or when the connection drops. A stale claim is taken over rather than
deadlocking the account, so a crashed login does not lock someone out. Eight
tests cover the claim, the release, the takeover and the expiry.

### The message you get when a tweaker breaks FML

`ModClassLoader` used to fail with a bare `ClassCastException` naming FML's own
classes when something initialized FML before launchwrapper handed over — which
reads like a fault in this core, and is not. It now names the loader that turned
up and points at the tweaker responsible, so the log blames what actually went
wrong. (This is what `lwjgl3ify` looked like when it was in the pack's `mods`
directory on a server launch.)

### Java 9+ without command-line flags

The server jar's manifest carries `Add-Opens`, so `java -jar <server>.jar` is
enough on a modern JVM — no `--add-opens` wall to paste into a hosting panel.
The start script builds its flags from the same list, so the two cannot drift.
The CI gate boots on Java 25 with **no** flags at all, which is the point: it
exists to prove the manifest works.

### Three gates that were passing on things they did not test

Each of these had gone green while the thing it claimed to check was broken:

- The modpack job booted a **daily build** nobody downloads while the release
  pack failed. It is now pinned to the release pack, and `gtnh-latest` is
  labelled as the early warning it is rather than a gate.
- The boot marker matched a mod's log line, so a server counted as up while it
  was still starting. It now anchors on vanilla's real `Done (Ns)! For help`.
- Shutdown was not checked at all. It now fails on `Exception stopping the
  server` — booting and saving are both part of working.

`CLAUDE.md` records the shape rule and these evidence standards, so the next
change goes through them.

### Java 25 with a modpack: still open

The core itself boots on Java 25 with no flags. **GT New Horizons on Java 25
does not**, and the cause has not been established. The same gate, same commit,
same pack, `modpack_java=25`, fails at mod construction:

```
LoaderException: java.lang.IncompatibleClassChangeError: Inconsistent constant
  pool data in classfile for class net/glease/tc4tweak/api/InfusionExtAPI$RecipeNBTBehavior.
  Method 'ItemStack lambda$mergeNBT$1(Set, InfusionRecipe, ItemStack, ItemStack)'
  at index 40 is CONSTANT_MethodRef and should be CONSTANT_InterfaceMethodRef
```

There are two possible explanations — shipped that way by the mod's own build,
or correct on disk and broken in flight by some coremod's transformer. This
core's own ASM call sites all pass an explicit `itf`, which rules out the obvious
version of the bug here, but that is not the same as knowing where it does come
from. Java 8 verifies this class fine; Java 9's verifier is the one that checks
it, which is why it only shows up on a modern JVM.
[#22](https://github.com/SashaGoncharov19/UltraMine-updated/issues/22) tracks it.
Until it is answered: **Java 8 for modpacks.**
