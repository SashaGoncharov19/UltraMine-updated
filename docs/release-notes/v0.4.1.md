## One module descriptor no longer costs a whole jar of mods 🔍

A patch release for a bug that hides in plain sight, because the server starts
anyway:

```
[WARN] Zip file log4j-api-2.17.2.jar failed to read properly, it will be ignored
java.lang.NullPointerException: ... the return value of
  ASMModParser.getASMSuperType() is null
    at ASMModParser.isBaseMod -> ModContainerFactory.build
    -> JarDiscoverer.discover
```

Mod discovery reads every class file in every jar on the class path, and the
loop that does it is wrapped in one try/catch **per jar** — so the first entry
that throws ends the scan and the jar is written off whole. What throws is a
module descriptor: `module-info.class` has no super type, and `isBaseMod`
dereferenced it. Multi-release jars have carried one since Java 9, and both the
ASM and log4j versions this core ships are multi-release.

For those jars it costs nothing — they contain no mods. **For a mod published
as a multi-release jar it costs the mod**: skipped in its entirety, with a
single warning as the only trace.

This is not a modern-JVM problem; it happens on Java 8 just the same. It became
reachable when the core's own dependencies were modernized.

### Fixed

- `isBaseMod` answers the question instead of crashing on it — a class with no
  super type is `java.lang.Object` or a module descriptor, and neither is a
  BaseMod.
- Both discoverers skip module descriptors, and the jar discoverer also skips
  `META-INF/versions/**`, where a multi-release jar keeps alternates of classes
  that also exist unversioned and whose entry names are not class names at all.
- A test builds a real module descriptor with ASM and pins the behaviour, next
  to the BaseMod checks it must not break.

## Three startup complaints that were never true here

The same boot log carries three more lines that read like something is wrong,
and are simply how this core is built. All three now say what is actually the
case, once, at the level it deserves — none of them is silenced:

- `[ERRO] The binary patch set is missing ... things are not going to work!`
  Stock Forge ships Minecraft unmodified and patches it at runtime from
  `binpatches.pack.lzma`. This core is a merged source tree — Minecraft, Forge,
  FML and UltraMine compiled together and reobfuscated — so the patches are
  already in the jar and there is nothing to apply. (The unpacker could not run
  on a modern JVM regardless: Pack200 was removed in Java 14.)
- `[ERRO] FML appears to be missing any signature data.` That check notices a
  tampered Forge jar by looking for the Forge project's signature on FML's own
  classes. Nothing here is signed by Forge — FML included, it is built from
  source — so the check can only ever come out this way. Integrity is published
  per release as SHA-256 sums and build provenance attestations. **The Minecraft
  certificate check next to it is untouched and still means what it says.**
- `SecurityManager is not supported by this JVM; continuing without FML's
  exit-trapping manager` undersold what still holds. Java 24 removed the
  Security Manager, but `System.exit`, `Runtime.exit` and `Runtime.halt` calls
  from mods are still trapped — `TerminalTransformer` rewrites them as the
  classes load, which is what the manager was there to back up.

Nothing else changed: same chunk storage backends, same build, same everything
else as [v0.4.0](https://github.com/SashaGoncharov19/UltraMine-updated/releases/tag/v0.4.0).
